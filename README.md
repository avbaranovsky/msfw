## Структура Shared Memory
Кольцевой буфер (Ring Buffer)Поскольку клиент будет «спамить» пакетами, нам нужна структура типа FIFO (First In, First Out), реализованная в виде циклического буфера фиксированного размера.В памяти shmem будет лежать единая структура, разделенная на две части:Управляющий заголовок (Metadata): Атомарные индексы/указатели для координации.Массив слотов под пакеты: Наш пул, куда записываются dummy_raw_packet.Примерная схема структуры в памяти:+-------------------------------------------------------------------------+
|                          УПРАВЛЯЮЩИЙ ЗАГОЛОВОК                          |
|  atomic_size_t head  --> Индекс для чтения сервером                     |
|  atomic_size_t tail  --> Индекс для записи клиентом                     |
|  size_t max_packets  --> Максимальная емкость буфера                    |
+-------------------------------------------------------------------------+
|                            ПУЛ СЛОТОВ ПАКЕТОВ                           |
|  Slot 0: [ Packet Data (40 bytes) | Status/Length ]                     |
|  Slot 1: [ Packet Data (40 bytes) | Status/Length ]                     |
|  Slot 2: ...                                                            |
+-------------------------------------------------------------------------+
Важный нюанс для highload: Переменные head и tail активно изменяются разными процессами (клиент двигает tail, сервер — head). Чтобы избежать false sharing (когда процессорные кэши постоянно инвалидируют друг друга из-за того, что переменные лежат на одной кэш-линии), их нужно будет разнести по памяти и выровнять, например, через alignas(64).

## Синхронизация и Многопоточность: Как не устроить коллапс
Вот тут начинается самое интересное. У нас многопоточный клиент (Multi-Producer) и многопоточный сервер (Multi-Consumer).Если использовать классический pthread_mutex с флагом PTHREAD_PROCESS_SHARED, мы получим бутылочное горлышко: все потоки всех приложений будут стоять в очереди за одной блокировкой. Скорость упадет.Есть два пути развития архитектуры:
Вариант А. На мьютексах и условных переменных (Проще, надежнее для CPU)Мы делим кольцевой буфер на критические секции с помощью межпроцессного мьютекса и используем pthread_cond для уведомлений.Плюс: Когда пакетов нет, потоки сервера честно «спят» в ядре и не жрут 100% CPU.Минус: Относительно медленно из-за переключений контекста (context switch) при вызове сисколлов синхронизации.
Вариант Б. Lock-Free на атомиках с упреждающим бронированием слотов (Spin-lock / Polling)Потоки используют атомарные операции (std::atomic или GCC-встроенные функции над индексами head/tail) с операцией compare_exchange_weak (CAS).Как это работает: Поток клиента, прежде чем писать пакет, атомарно увеличивает tail на 1, тем самым «бронируя» за собой конкретный слот в массиве. После этого он спокойно пишет туда данные без всяких блокировок. Сервер делает аналогично с head.Плюс: Бешеная скорость, честный Zero-Copy и Lock-Free.Минус: Потоки сервера должны постоянно крутиться в цикле (polling/busy wait), проверяя появление новых пакетов, что загрузит ядра процессора на полную мощность.

## Как это стыкуется с многопоточностью сервера
Раз уж сервер многопоточный, кольцевой буфер shared memory идеально ложится на схему параллельного разбора:Каждый рабочий поток сервера независимо обращается к общей памяти, атомарно «откусывает» себе индекс пакета из головы (head), забирает его на проверку по правилам файрвола и обновляет таблицу состояний соединений (conntrack).
